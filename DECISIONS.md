# Engineering decisions

Approximate active time: 1–2 hours across design, implementation, tests, and review. The assignment is intentionally scoped to the highest-risk invariants.

## Invariants

1. A cart produces at most one order. An identical checkout retry returns that order and never decrements stock again.
2. Product stock never becomes negative, including when different carts buy the last unit concurrently.
3. An order's line snapshots and money totals explain the purchase after catalog changes. `gross = discount + net`.
4. One coupon exists per eligible order milestone, and a coupon is linked to at most one successful order.
5. A failed checkout commits no order, inventory reduction, or coupon redemption.
6. The report aggregates one consistent view of committed orders, lines, and coupons. `generated = available + redeemed`.

## Semantics selected for unspecified behavior

- A cart does **not** reserve stock or freeze price. `GET /carts/{id}` returns current prices and availability. Checkout requires the returned quote token. A changed cart, product name, or price produces `409 STALE_QUOTE`; a stock change is checked separately as `409 INSUFFICIENT_STOCK`.
- `PUT /carts/{id}/items/{product_id}` sets an absolute quantity. Repeating the same value is a no-op. Removing a missing item is `404`.
- Checkout represents immediate payment success; no external payment action occurs. A same-cart request with a different quote or coupon after success receives `409 CART_ALREADY_CHECKED_OUT`.
- A coupon is generated by an explicit admin request **after** the milestone order has committed. One request generates one coupon for the oldest unrewarded eligible milestone. Repeated generation without a new eligible milestone returns `409`.
- A generated coupon is transferable, has no expiry or customer binding, and is reusable only until its first successful checkout. Codes are normalized to uppercase on checkout. A coupon can be used on the order that crosses a later milestone if it was already generated from an earlier one.
- Coupon discount is a whole percent of gross. A 100% discount is valid and can reduce net to zero. Product quantities in the report include only successful purchases, not carts or failed attempts.

## Decision: PostgreSQL and a modular monolith

**Context:** Multiple API workers must preserve inventory, cart, and coupon rules under overlap.

**Options considered:** In-memory locks, SQLite, a distributed service split, and one PostgreSQL-backed service.

**Choice:** A FastAPI modular monolith with PostgreSQL, SQLAlchemy, and Alembic. Routes handle HTTP, services own transactions and rules, repositories own queries, and models describe storage.

**Why:** PostgreSQL row locks, transactional updates, and uniqueness constraints work across the two configured API workers without a new coordination service. The small domain does not justify networked microservices.

**Consequences:** The Compose setup includes a database. Modules can be split later only after defining their transaction boundaries and event delivery.

## Decision: Explicit quote validation and immutable order snapshots

**Context:** Product price can change between adding to cart and checkout.

**Options considered:** Freeze price on add, silently charge the current price, or require a current quote.

**Choice:** A deterministic SHA-256 quote token covers cart version and current product IDs, names, quantities, and prices. Checkout locks and rereads products, compares the token, then snapshots name, quantity, price, and line total into `order_lines`.

**Why:** A client sees and accepts the amount it will pay. Catalog edits cannot rewrite an existing order's explanation.

**Consequences:** A name-only change also invalidates a quote. Tokens are stale-state markers, not signed authorization credentials. The API prevents order edits; database roles or triggers would be needed to enforce append-only storage against direct SQL writes.

## Decision: Cart-scoped checkout idempotency

**Context:** A client can time out after a successful commit and retry, or submit two attempts at once.

**Options considered:** A separate idempotency-key table, deduplication by request timing, or one order per cart.

**Choice:** Checkout locks the cart row, stores a fingerprint of the normalized quote token and coupon code, and enforces a unique `orders.cart_id`. The same fingerprint returns the stored order with `200`; a different fingerprint is a `409` conflict.

**Why:** A cart is single-use by business rule, so its ID is already a natural idempotency scope. The database unique constraint is a final guard.

**Consequences:** Clients must create another cart for a different purchase. If multi-checkout carts or payment attempts were introduced, an explicit idempotency key and payment state machine would be needed.

## Decision: Row locks plus conditional inventory updates

**Context:** Different carts can buy the last unit simultaneously.

**Options considered:** Process-local mutexes, serializable transactions with broad retries, optimistic versioning, and row locks.

**Choice:** A checkout locks its cart, then product rows in ascending product ID order, then the coupon row if supplied. It verifies stock and executes `UPDATE ... WHERE stock_quantity >= quantity` in the same transaction as order insertion. Database checks prohibit negative stock.

**Why:** Locks work across processes. Stable product ordering reduces deadlock risk; the conditional update and check constraints backstop the service logic.

**Consequences:** Very hot products serialize purchases, which is correct for exact inventory. A large-scale system could partition inventory by location or use reservations with expiry, while keeping a transactional source of truth.

## Decision: Milestones and single-use coupons in the database

**Context:** Two admins may generate at once, and two checkouts may redeem the same coupon.

**Options considered:** A background scheduler, in-memory counters, coupon `used` flags, or relationships to committed orders.

**Choice:** A singleton reward policy stores `n` and `x` once. Generation locks that row, counts committed orders, and inserts the next milestone with a unique milestone number. Redemption locks the coupon and stores its ID on the successful order; `orders.coupon_id` is unique.

**Why:** The coupon's redemption state follows the committed order, so rollback leaves it available. Row locks and unique constraints handle competing workers. A generator that sees an uncommitted milestone order may return `409`; a later request succeeds after that order commits.

**Consequences:** Generation is explicit and produces at most one coupon per call. The singleton row serializes generation, while ordinary checkout does not lock it. Changing the policy requires an intentional migration or admin operation; reseeding does not rewrite previous policy or coupon percentages.

## Decision: Integer cents and deterministic rounding

**Context:** Floating-point percentages can make order totals disagree by a cent.

**Options considered:** Binary floating point, `Decimal` with a currency context, or integer cents.

**Choice:** Store money as signed 64-bit integer cents. Validate a cart gross fits that range. For percentage `x`, calculate `(gross_cents * x + 50) // 100`, which rounds half cents up. Store gross, discount, and net on the order; database checks require nonnegative values and reconciliation.

**Why:** Arithmetic and retry results are deterministic with no floating-point drift. The product prices and percent are nonnegative and at most 100%, so discount cannot exceed gross.

**Consequences:** This assumes one currency (USD) and whole-percent discounts. Multi-currency pricing and more complex promotions need an explicit currency/rounding model.

## Decision: One read-only reporting snapshot

**Context:** Separate queries for orders, lines, and coupons could observe different checkout commits.

**Options considered:** A materialized summary, one complex SQL statement, default `READ COMMITTED` queries, or a read-only snapshot transaction.

**Choice:** `GET /admin/report` performs its aggregates in a PostgreSQL `REPEATABLE READ, READ ONLY` transaction.

**Why:** Every figure describes the same committed point in time. A test commits an order between the first and second aggregates and confirms the first report stays consistent while the next report sees the order.

**Consequences:** The report performs live aggregation and will become more expensive as order volume grows. At scale, add indexes, a replica or maintained projection, and an explicit freshness contract.

## Decision: Stable business error codes

**Context:** Clients need to distinguish a stale quote, sold-out item, used coupon, malformed request, and missing resource.

**Options considered:** Free-form messages only, HTTP status alone, or a structured error body.

**Choice:** Expected domain and validation errors return `code`, `message`, and `details`, with `404`, `409`, or `422` as appropriate. The API document names each important code.

**Why:** Machine-readable codes support reliable client behavior while messages and details aid humans.

**Consequences:** Database outages and unexpected programming errors currently use framework server errors. Production would add request IDs and a uniform infrastructure error handler.

## Implemented and deferred

Implemented: product seed, carts and quotes, transactional checkout, immutable order snapshots through the API, order reads, milestone generation, single-use coupons, consistent reporting, migrations, focused PostgreSQL concurrency tests, a repeatable isolated demo, linting and formatting, and a locked `uv` environment.

Deferred: authentication/authorization for `/admin`, a real payment provider, reservations, cancellation/refunds, coupon expiry/ownership, rate limits, observability, and operational backup/restore. These are production concerns; they are not required to demonstrate the assignment's core invariants. The local Compose database user has broad permissions for setup and the demo; production would separate migration and runtime roles.

## Multiple instances and scale

The invariants rely on PostgreSQL transactions and constraints, so more stateless API instances can share one database. A load balancer and independently scaled worker replicas need no process-local locks. Pool sizing and lock wait times should be measured under load. For a larger catalog and reporting volume, add query indexes, pagination, an order-event outbox for downstream consumers, and a projection or replica for reporting. Real payment would require an idempotent provider key and a durable pending/confirmed/failed state machine; the database transaction cannot span a remote payment call.
